# Mino v0.3 design milestone

The v0.3 milestone completes the planned local Mino design while the crate and
plugin remain version `0.1.0`. Mino is a deterministic plan protocol engine for
coding agents, not a plan-template generator and not an agent model. All state,
approval, evidence, execution, standards, review, and Git behavior remains
explicit, local, revision-bound, and inspectable.

## Complete capability map

The global command inventory is executable through recursive `--help` tests and
`mino agent capabilities`. The complete design is organized as follows:

- Project and protocol: initialize, diagnose, scan, show, migrate a pinned
  protocol, analyze legacy workflow files, and conservatively import one legacy
  plan into a new Draft.
- Standards: detect, recommend, apply, explicitly sync a verified catalog,
  author static team catalogs, and resolve source-bound conflicts through an
  approval boundary.
- Plans: author or apply a Draft, validate, finalize, review, approve, execute,
  checkpoint, record evidence, block/resume, finish, review/rework/accept,
  propose protected amendments, fork exact historical revisions, compare
  semantic differences, and archive an unselected plan without deletion.
- Observation: run one planned check or monitor it in the foreground under
  finite attempt/interval/deadline bounds. Emit an inert, digest-bound scheduled
  task specification without contacting a scheduler.
- Local Git: inspect and bind a worktree, create only an explicitly approved
  deterministic branch, make only an eligible plan-scoped task commit, and
  optionally install marker-owned advisory pre/post commit hooks after a
  separate approval.
- Distribution: validate a canonical Codex plugin source and create
  deterministic target-native ZIP artifacts that embed exactly one compatible
  CLI, Skill, launcher, protocol identity, standards set, and license set.

The detailed command and machine-schema contract remains in
`docs/command-contract.md`. `docs/team-catalog.md` and
`docs/distribution.md` define the two final operator workflows.

## Trust and approval boundaries

Mino never derives authorization from conversational tone, a previous
approval, Git Flow consent, or the mere existence of a plan. The protected
boundaries are plan approval, Material amendment approval, plan archive,
standards-conflict resolution, final review acceptance, local branch creation,
and hook installation. Each requires the current state and an auditable
reference where its command contract specifies one.

Every mutation uses the current revision and an idempotency request ID. Managed
Markdown is a projection; `.mino/**` is the source of truth and must not be
edited manually. Planned processes use exact argv with finite timeout/output
limits and immutable evidence. Team standards trust canonical HTTPS bytes and
digests. Native plugin trust binds source, binary, protocol, capabilities,
standards, target, and archive inventory into one manifest.

## Release verification

The release proof is layered:

1. v0.1 E2E installs and drives the core plan/evidence lifecycle.
2. v0.2 E2E drives standards conflicts, Material amendment and reapproval,
   exact Git Flow commits, review rework, and final acceptance.
3. v0.3 E2E packages the native plugin entry, builds and synchronizes a
   loopback-only test catalog, proves sync does not implicitly activate all team
   packages, resolves the separate built-in standards application, emits a
   bounded scheduled-task handoff, monitors a planned check, completes an
   audited plan, then forks and diffs retained history.
4. Contract suites verify hooks, plan variants, monitoring, scheduling,
   catalogs, plugin compatibility, deterministic artifacts, command inventory,
   docs, migrations, storage recovery, runner limits, and adversarial paths.
5. Format, strict Clippy, dependency ordering, Rustdoc warnings, tests, and Miri
   form the repository quality gate. Non-host native plugin jobs remain an
   external CI observation and must not be reported as locally executed.

Local E2E network traffic is confined to an in-process loopback static server;
the production CLI still requires HTTPS for explicit standards sync. Native
plugin smoke uses no network.

## Upgrade from earlier milestones

No destructive state rewrite is introduced by v0.3.

1. Build or install one complete compatible `mino 0.1.0` artifact.
2. Run `mino protocol status --format json --no-input` in the project.
3. If a pinned protocol migration is reported, review it and invoke only the
   exact supported `protocol migrate` operation. Never copy protocol Markdown
   as a fallback.
4. Run `mino project doctor`, then `mino agent context`.
5. Keep existing plans, evidence, review history, Git journals, and standards
   locks. New plan-variant, monitor, schedule-spec, hook, and catalog commands
   are additive and do not authorize themselves.
6. If adopting team standards, configure the reviewed HTTPS catalog, explicitly
   sync it, inspect recommendations/conflicts, and apply through the normal
   plan flow.
7. If adopting the Codex plugin, replace the entire verified target bundle and
   run its declared compatibility probes. Do not mix old and new files.

Rollback uses the prior complete binary/plugin artifact and the retained
project state. A failed catalog sync preserves the active cache. A failed
artifact build publishes no target directory. A blocked plan resumes through
its recorded state; it is never repaired by deleting evidence or Git state.

## Explicit non-goals

The completed v0.3 design intentionally provides none of the following:

- No LLM execution, prompt inference engine, or autonomous agent loop.
- No daemon, background worker, unbounded watcher, or hidden polling process.
- No cloud control plane, telemetry, account service, or Web UI.
- No built-in scheduler and no external task creation without separate user
  authorization; `exec schedule spec` emits inert local data only.
- No auto-update, package discovery, marketplace publication, download
  fallback, or arbitrary plugin runtime.
- No shell-string execution for planned checks.
- No Git push, merge, rebase, reset, amend, force-push, tag creation, branch
  deletion, or worktree creation/deletion.
- No plan merge, implicit approval, silent standards conflict merge, or manual
  editing of managed state.

These absences are product boundaries, not future behavior implied by this
release. Any expansion requires a new explicit design, plan, authorization
model, and verification contract.
